\section{Introduction}
\subsection{Purpose}
This Software Design Document (SDD) explains the architecture and implementation approach for the RoboSub LA Wailord software system. It is based on the Cal State LA Ascent RoboSub project page and the linked Fall 2025 RoboSub SRS and SDD resources. It is intended for developers, reviewers, operators, and future teams who need to understand how computer vision, navigation, autonomy, controls, simulation, website support, and hardware communication fit together.

\subsection{Design Goals}
\begin{itemize}[leftmargin=*]
  \item Separate major RoboSub responsibilities into modules that can be developed and tested independently.
  \item Use explicit message contracts between computer vision, autonomy, controls, navigation/state estimation, and hardware interfaces.
  \item Support simulation-first validation before physical vehicle testing.
  \item Make setup and dependencies reproducible through Docker and documented package lists.
  \item Preserve safety by bounding commands, detecting stale inputs, and requiring operator-controlled hardware enablement.
\end{itemize}

\section{System Overview}
The RoboSub system is designed as a ROS 2 Humble based robotics application running primarily on a Jetson Orin Nano with low-level support from a Teensy 4.1 microcontroller. Each subsystem runs as one or more nodes. Nodes exchange messages through topics and use services or actions for commands that require acknowledgement. The operator interacts with the project through repository documentation, command line launch scripts, Jira task tracking, the RoboSub LA website, and Unity HDRP or Gazebo Fortress simulation tools.

\subsection{Architectural Pattern}
The design uses a modular publish-subscribe architecture. Computer vision, navigation and state estimation, autonomy, controls, simulation, website support, and hardware output are separate modules with defined responsibilities. This pattern reduces coupling because a simulated camera can replace a physical camera, and a simulated thruster model can replace the physical Teensy and thruster interface during testing.

\subsection{Data Flow}
\begin{enumerate}[leftmargin=*]
  \item The operator launches the system using a documented ROS 2 launch file or Docker entrypoint.
  \item Camera, MS5837, IMU, and optional simulated sensor drivers publish raw input topics.
  \item Computer vision and state estimation nodes convert raw input into detection and vehicle state messages.
  \item The autonomy node evaluates mission state and chooses the next behavior.
  \item The controls node converts the desired behavior into bounded motion commands.
  \item The hardware interface sends commands to the Teensy 4.1 and thruster controller, or the simulation consumes the commands in a virtual environment.
  \item Logging records configuration, events, warnings, and test outcomes.
\end{enumerate}

\section{Detailed Design}
\subsection{Computer Vision Subsystem}
The computer vision subsystem receives low-light camera frames and publishes mission object detections. It uses OpenCV for image processing and YOLOv7 for object detection. A detection message should include object type, confidence, bounding box or center point, timestamp, and frame ID. The subsystem should support at least two input modes: live camera and recorded or simulated image stream.

\subsection{Navigation and State Estimation Subsystem}
The navigation and state estimation subsystem combines IMU readings, MS5837 pressure sensor readings, and optional visual estimates. The output is a Wailord state message containing depth, heading, roll, pitch, yaw, timestamp, and freshness metadata. Consumers must reject stale state messages.

\subsection{Autonomy Subsystem}
The autonomy subsystem uses a mission state machine. Representative states include initialize, search, align, approach, execute task, recover, and complete. Transitions must be based on explicit events such as target detected, confidence threshold met, timeout reached, or safety fault raised.

\subsection{Controls Subsystem}
The controls subsystem converts autonomy goals into thruster commands. The control layer may use PID controllers and a thruster solver for depth, heading, and translation. All output must pass through command validation before reaching hardware. Validation includes min and max bounds, rate limits, stale input checks, and hardware enable state.

\subsection{Hardware Interface Subsystem}
The hardware interface hides low-level communication details from the rest of the system. It translates bounded commands into Teensy 4.1, PWM, GPIO, serial, or custom board messages. It also reports acknowledgement, fault, or timeout information back to the logging and state systems.

\subsection{Simulation Subsystem}
The simulation subsystem provides a Unity HDRP or Gazebo Fortress virtual pool, Wailord vehicle model, simulated sensors, and mission objects. Its purpose is not to prove real-world performance. Its purpose is to catch integration errors, missing messages, bad launch configuration, and obvious mission logic issues before hardware testing.

\subsection{Website Subsystem}
The website subsystem presents public information about RoboSub LA. It should include pages for Home Port, The Fleet, Sponsors, Crew, Resources, and Updates. It supports recruitment, sponsor visibility, project history, and handoff by giving future students a centralized public reference.

\subsection{Documentation and Tracking}
The repository contains the SRS, SDD, design specification, user manual, snapshot objectives, workflow diagram, and TestRail-style reports. Jira is used to track tasks and snapshot work. TestRail is used, or represented in exported report form, to connect requirements to test cases and results.

\subsection{Message Contract Guidelines}
\begin{itemize}[leftmargin=*]
  \item Every message that affects control must include a timestamp.
  \item Frame IDs must be included when the message depends on a physical coordinate frame.
  \item Confidence values must use a documented range from 0.0 to 1.0.
  \item Hardware command messages must include limits or be validated against configured limits before output.
  \item Fault messages must include subsystem name, severity, timestamp, and recommended operator response.
\end{itemize}

\section{Deployment Design}
\subsection{Development Environment}
Development should run on Kubuntu 22.04.5 LTS, Ubuntu 22.04, or a Docker image based on Ubuntu 22.04. Developers should install ROS 2 Humble, Python 3.10, C++ build tools, OpenCV, YOLOv7 dependencies, PyTorch, Colcon, CMake, Gazebo Fortress, and Unity tooling where needed. GPU-specific packages should be optional so the documentation remains usable on non-Jetson development machines.

\section{Error Handling and Safety}
\begin{itemize}[leftmargin=*]
  \item If camera, depth, or IMU data becomes stale, autonomy must stop advancing mission state and controls must enter hold or safe output.
  \item If the hardware interface reports a fault, autonomy must transition to recover or abort.
  \item Thruster commands must be clamped to configured limits.
  \item Hardware enablement must be explicit and visible to the operator.
  \item Logs must capture safety faults with timestamps and subsystem names.
\end{itemize}

\section{Design Rationale}
The selected design emphasizes modular robotics patterns because RoboSub work is usually divided among subteams. Computer vision, controls, autonomy, hardware, and simulation teams can work in parallel if interfaces are stable. Simulation-first testing reduces risk by catching integration errors before water testing. Docker and documented package lists reduce setup uncertainty for future teams.
